### A. 架构目标与总体职责

目标：让代码好读、好找、好加、好扩展，支持后续动画、音效、DLC 和维护。组合使用状态机、仲裁和黑板，不因功能增长堆积隐式副作用与深层嵌套。

整体按 UI／输入、Logic、Data 分层。状态机、仲裁、效果处理是 Logic 内部职责，不是三个相互独立的顶层；Physics 承担物理执行，Presentation 承担显示。当前 `StateMachine/`、`Blackboard/`、`Templates/` 等目录是实现组织，不自动等于依赖许可。

| 职责 | 可以做什么 | 禁止／边界 |
| --- | --- | --- |
| UI／输入 | 接收设备或面板操作，转换并提交逻辑请求；玩家与 AI 使用统一 Entity 和输入接缝 | 不直接赋值角色能力、扣血或实施技能；不得接收下层越权修改输入行为 |
| EntityBrain | 编排输入、仲裁、状态和效果处理；接入明确的结算入口 | 不能成为随意堆放共享状态或具体功能的万能类；新字段／方法需说明职责 |
| EntityCapabilities | 判断移动、跳跃、技能等是否允许，收拢通用条件 | 判断不应偷偷施加效果、修改数据或执行 Debug 操作 |
| 状态机及状态对象 | 校验转换是否合法，管理层级、互斥、起止、持续与流转 | 不直接赋值生命、能力、Buff 效果；不在状态内混入具体效果执行逻辑 |
| 效果／行为逻辑 | 实施移动、攻击、技能、Buff，计算参数并经 Data API 提交更新；负责效果施加与移除 | 不绕过必需的资格判断；不能把副作用藏进查询方法 |
| Data／黑板 | 保存当前事实、资源与实例数据，提供受控读写接口，执行数据提交 | 不主动选择行为、改角色能力或执行玩法；禁止反向修改／驱动上层 |
| Presentation | 展示相机、动画、音效、UI 与反馈，管理自己的显示对象 | 不直接修改玩法数据；交互操作走逻辑请求入口 |
| Debug | 专属目录和独立模块，开启 Debug 才接入仲裁，具体调试操作由 Debug 模块执行 | 不让调试效果散落在输入、Brain、Capabilities 或状态中；仲裁只当裁判 |

玩家和怪物共用 Entity；差异来自输入源、配置和装备。玩家设备产生指令；AI 决策树约每 0.2 秒评估后产生指令，这个间隔是会议示例／可配置节奏，不是全系统固定 Tick。

### B. 数据流与读写底线

```text
玩家 / AI / UI 请求
    → Brain 编排与 Capabilities 资格判断
    → 需要状态的行为申请转换，状态机内部校验合法性
    → 状态生效 / 持续 / 结束
    → 逻辑模块实施效果并调用 Data API
    → Data 更新并保存数据
```

- 上层可以按职责经接口读取、写入黑板。**单向约束不是“禁止上层读取下层”**，而是禁止下层越权改上层或主动发起上层玩法。
- “Data 不自我修改”指不自主推进玩法；不禁止外部调用的数据写入口。逻辑层计算和组织效果，Data 接口负责记录／提交，不在 Data 的更新方法里顺带触发技能或修改状态机。
- UI 面板改技能：UI 请求逻辑 API → 必要的资格／装备条件检查 → 逻辑调用槽位写接口 → Data 更新槽位；禁止面板直接改能力或 Data 因槽位变化自行施加技能效果。
- 共享 ScriptableObject 模板只读；每实体的生命、冷却、Buff 剩余时间等运行状态独立保存，避免复制多份同一事实。
- 黑板是信息职责，不强制必须有一个大型 Blackboard 类。原表的五块窄黑板是已记录的实现组织；会议没有拍板重新集中成一个对象。具体归属及哪些运行过程需从 Blackboard/ 拆至 Logic 仍需审查。
- 伤害继续通过 `EntityBrain.TakeDamage`／`ResolveHit` 的现有结算入口，不因重构直接绕过入口写 Vitals。

### C. 状态机与仲裁的最终分工

15:34～15:36 曾讨论到期后直接修改与通知逻辑两种方式；15:41 的最终原则是 **“状态机只管流转，逻辑层负责赋值”**。因此效果的施加与移除都归逻辑处理。状态如何通知逻辑（事件、协调者调用等）尚未确定，不能把任一通信实现写成已批准方案。

- Capabilities 做通用行为资格校验；状态机内部仍检查转换条件。先区分两者规则归属，不能各自重复一套完整 if 链。
- 状态机可维护自身生命周期和层槽；“不改角色数据”不意味着禁止维护自己的状态。
- 状态／Buff 开始、生效、持续、结束与效果实施分开。状态机不直接给实体加攻击力、扣血或恢复数值，逻辑经数据接口更新效果记录。
- 层级、压制和转换规则应明确，不能把状态机退化成单纯计时器，也不能以“校验”为由把全部玩法移入状态类。

### D. 功能示例与扩展接缝

**跳跃**：Capabilities 先拦“死亡／被控制等情况下不能跳”；转换是否合法由状态机核查；效果逻辑提供跳跃倍率等参数；物理执行完成运动。“能否跳”和“跳多高”分开，不依赖一个可能缺失的具体状态对象去取倍率。修饰效果的缺省／合法参数需有明确策略。

**射击组合**：瞄准、射击、换弹作为可独立配置的能力／技能。进入瞄准后由逻辑添加“瞄准中”Buff／标记，退出后由逻辑移除，标记供判断只读使用。标记与状态转换的同步顺序、互为条件时如何避免循环，需在实现方案中定义，不能凭空假定已解决。没有某项能力不应自动得到对应功能；此例不自动要求现在新增射击玩法。

**技能与命中**：尝试释放 → 资格判断 → 对应攻击／技能状态成功进入 → 逻辑施加自身效果。失败请求不得残留效果。自身增益与目标效果分别配置；目标效果需要实际有效命中，未命中不得给假定目标挂 Debuff。召唤等特殊执行由其逻辑负责，不统一简化为自身 Buff。

会议提出 TryCastSkill 返回命中目标作为扩展思路，但命中可能发生在前摇之后。**不得把释放成功当成已命中**；返回目标还是后续命中结果通知，需要根据技能时序明确后再实施。

**Debug 与功能归位**：Debug 专属目录，关闭时不接入仲裁／调试执行；关闭调试不应影响正常附身等玩法。附身等复杂功能应有容易查找的入口与组织，具体迁移目录需结合引用、Unity `.meta`／GUID 和测试制定方案，不在本轮凭空规定目录。

### E. 可读性与架构审查闭环

开发流程：**确定需求与方案文档 → 实现 → 按架构审查 → 修正 → 复审通过 → 下一功能**。每次大量生成／变更后必须审查；审查通过是门槛，不用编译或测试通过代替。当前阶段暂缓分支合并，GitHub 对接研究不表示已授权同步／合并。

可读性优化必须针对代码证据：减少过深 if 嵌套，采用清晰步骤与适当提前返回；判断与副作用分离；整理重复条件归属；让入口、失败路径、执行顺序和结果可追踪。会议中的“无限嵌套”是问题描述，不是已证明全项目递归失控。重构默认保持玩法，行为变化单独说明与验证，不用增加抽象或拆碎方法替代可读性。

AI 动手前需回答：放在哪个模块？谁仲裁？谁管理状态？谁施加／移除效果？谁经接口写哪份数据？哪些接口尚未确认？改完检查越权、重复校验、隐藏副作用、时序、模板／实例混用、Debug 泄漏与功能可定位性，再运行适当检查。

## 0. 一句话架构

**状态机答"现在在做什么"，仲裁答"允不允许"，黑板答"共享状态是什么"。**
旧三件套在本项目里的受控形态：黑板拆成了五块窄黑板（指令 / 标签 / 体质 / 装备 / 效果实例），
仲裁收进三层闸门（能力 → 数据 → 入口），状态机保留为分层 + 两遍 Tick。
目录已按域归位：

```
Entity/
  Entity.cs / EntityBrain.cs / PossessionLink.cs / DebugSystem.cs   组合根 + 编排者 + 会话关联 + 调试开关
  StateMachine/        状态机域（机器 + 基类 + 层定义 + States/ 七状态）
  Blackboard/          五块窄黑板的载体类
  Templates/           SO 配置模板（9 个 SO + 配置枚举）
  Logic/               仲裁与推导投影（EntityCapabilities / FaithEvent / MeleeAttackHits / ArmorSetBonusList / IPossessionEffect）
  Input/  Physics/  Presentation/    输入源 / 运动+命中查询 / 表现
```

每个类只归属一个域；跨域的只有 EntityBrain（编排者，见 §1.5 警示）。

## 1. 状态机域（"现在在做什么"）

| 类 | 层/角色 | 职责 | 读谁·写谁 |
|---|---|---|---|
| `StateMachine/EntityStateMachine` | 层槽容器 | 每层一个活跃状态：同层互斥、异层叠加；两遍 Tick；层清空 | 写层槽（**写者两个：状态自身转换 + Brain，见 §11**） |
| `StateMachine/EnumStateLayer` + `EnumStateLayerRules` | 层定义 | 四层枚举（Locomotion/Aerial/Action/CrowdControl）+ CC 压制规则（冻结不清除） | 纯静态规则 |
| `StateMachine/EntityState` | 状态基类（唯一继承点） | Enter/Exit 生命周期、HandleTransitions（纯转换）/Tick（纯动作）契约；能力声明 `GrantsSuperArmor`/`LocksMovement`；共享移动出口 ApplyLocomotion | 读 CommandBuffer/Motor/Modifiers |
| `StateMachine/States/LocomotionStates`（Idle/Walk/Sprint） | Locomotion 层 | 按移动指令与加速开关互转；速度经 ApplyLocomotion（乘法链 ×出招表修正） | 读指令；写 Motor.MoveHorizontal |
| `StateMachine/States/AerialStates`（Grounded/Air） | Aerial 层 | 只判起跳/离地/落地时机，无动作 | 读 Motor.IsGrounded |
| `StateMachine/States/EntityAttackState` | Action 层 | 通用连段执行器：前摇→命中→后摇计时、续段取消窗口、起手快照出招表（防换装串段）、命中窗口区间相交采样 | 读指令（续段）；写 Tags（Swinging 挂/摘）、调 MeleeAttackHits |
| `StateMachine/States/EntityStunState` | CrowdControl 层 | 失控默认呈现：站桩 + 轮询 `HasControlActive` 自清（时长职责在 ModifierList） | 读 ModifierList |

**放置规则**：新行为状态 = `StateMachine/States/` 新 sealed 类 + 层归属（新行为维度才加层枚举）+ 构造期能力声明；
转换逻辑只准写在 `HandleTransitions`（只调 Machine.ChangeState/ClearState），动作只写在 `Tick`。
新失控种类 = 枚举成员 + 新 CC 状态类 + Brain 注册表一行（全"加"零"改"）。

## 1.5 EntityBrain——编排者（多重身份警示）

`EntityBrain` 是全项目唯一跨域类，现行合法身份三个：
① 每帧管线编排（唯一 Update，顺序勿调）；② 仲裁**执行**者（消费指令时调 Capability，不做裁决；
失控呈现投影 `SyncControlProjection` 也在这里——ModifierList 变更时回调，层槽写入统一收口）；
③ 结算入口（TakeDamage 伤害唯一入口 / ResolveHit 命中结算 / TryCastSkill 技能执行）。
附身会话的**关联存储已拆归 Entity**（审视 #7）：`ActivePossession`/`DeathView`/`LastSkillCast`
存 Entity（写者仅 Brain 与 PossessionLink），Brain 侧只留只读转发（IsPossessing/PossessionRemaining/
HasSoulOut/HasPlayerView/LastSkillCast）保既有调用点稳定。
后续往 Brain 加字段的门槛：它必须回答"这是编排本身吗"——不是就放对应域。

## 2. 仲裁域（"允不允许"）

三层闸门，从外到内：

```
请求（指令/命中/施加效果）
  → ① 能力闸门 EntityCapabilities：活着？失控？动作占用？（通用，与数据无关）
  → ② 数据闸门 SkillSlot.CanCast / WeaponSlot.CanEquip / SkillSO.IsAttackConfigurationValid：
       装了吗？冷却？信心到阈值？容量够？（纯数据，Data 层自查）
  → ③ 入口闸门（分散在入口处的完整性检查）：
       TryBeginPossession 的会话条件、MeleeHitQuery 的参数合法性、
       FaithEvent 的方向/一次性、ModifierList.Apply 的霸体仲裁（施加时刻定死）
```

| 类 | 仲裁内容 | 备注 |
|---|---|---|
| `Logic/EntityCapabilities` | CanMove / CanUseSkill / CanCastSkill / CanJump / IsControlled / HasControlImmunity | **新门禁（装备要求/资源不足类通用规则）改这里，调用点不动** |
| `Blackboard/SkillSlot` | CanCast（冷却+阈值+配置校验）/ Consume（二次校验后提交） | 数据侧技能闸门 |
| `Blackboard/WeaponSlot` | CanEquip（双手容量和 ≤ 上限） | 装备闸门 |
| `Templates/SkillSO` | IsAttackConfigurationValid（段位参数纯配置校验） | 资格 UI 与释放共用 |
| `EntityBrain.TryBeginPossession` | 会话互斥/双方存活/资产角色与纯度（17 条件——审视 #4 建议分组） | 附身闸门 |
| `Logic/MeleeAttackHits` | 目标归并（排除自身/死亡/停用/重复）+ 阵营敌我判定 | 敌我=非零且不同（用户钦定：操控权与阵营解耦） |
| `Physics/MeleeHitQuery` | 查询参数合法性（NaN/Infinity/非法角度拒绝） | 纯 Physics |
| `Logic/FaithEvent` | 方向（Crown=+1/Tide=-1）、同实例一次性、死亡不结算 | 信心唯一写入通道 |
| `Blackboard/ModifierList.Apply` | 霸体拦控制成分（施加时刻定死，免疫≠解控） | |

## 3. 黑板域（"共享状态是什么"）

五块窄黑板，**每块有唯一写口**——这是本架构的核心纪律：

| 黑板 | 载体类 | 内容 | 唯一写口（谁可以改） | 主要读者 |
|---|---|---|---|---|
| 指令 | `Blackboard/CommandBuffer` | 电平（Move/Look/Sprint/Aim）+ 边沿（Jump/Possess/Attack/Skill） | 输入源 GatherCommands；Brain 帧首 ResetLevels、消费点清边沿 | Brain、状态、AttackState |
| 标签 | `Blackboard/CharacterTagSet` | 64 位命名标签 | 状态直写（Add/Remove，位域 A）+ ModifierList.SyncTags（容器投影，位域 B）——两域互不踩脚 | TakeDamage（Swinging 解释器）、任意查询 |
| 体质 | `Blackboard/CharacterVitals` + `SkillResource` | HP / 信心 / 死亡事实 | ApplyDamage/ApplyHeal（Brain.TakeDamage 与 ResolveHit 吸血调用）；信心只经 FaithEvent 与 Consume.Reset | 表现层（事件订阅）、SkillSlot |
| 装备 | `Blackboard/CharacterSlotContainer` + Weapon/Skill/Armor/Accessory 四槽 | 有什么装备、冷却剩余 | TryEquip/Unequip 族 + EquipmentChanged 事件 | ArmorSetBonusList、AttackState、Brain |
| 效果实例 | `Blackboard/ModifierList` 条目 | 剩余时长/层数/跳伤与信心累加器 | Apply/Dispel/Remove/ExtendDuration；Tick 到期自清 | 乘法链读点（GetStatMultiplier 等） |

辅助状态载体（不成其为独立黑板，但同样有写口纪律）：
**Entity 的会话/视点状态**（`ActivePossession` 附身关联、`DeathView` 死亡观战、`LastSkillCast` 技能快照——
写者仅 Brain 与 PossessionLink；派生查询 IsPossessing/PossessionRemaining/HasSoulOut/HasPlayerView 在 Entity，
Brain 留只读转发）；`Physics/EntityMotor`（IsGrounded/VerticalVelocity：Motor 自身与 Brain.TryConsumeJump 写）；
`Entity.startPlayerControlled`（只被 Bootstrap 读一次，运行时控制状态唯一真相是 `Brain.InputSource`）。

**放置规则**：新共享状态先问属于哪块黑板——指令→CommandBuffer 字段；数值→对应槽/资源类；
命名状态→EnumEntityTag + TagSet；持续效果→ModifierEffect 资产；会话/身份级→Entity（internal 写口）。
**禁止**在 Brain / 状态类上加 public 字段充当共享状态（那是旧黑板病复发）。

## 4. 输入域（"谁在下指令"）

| 类 | 职责 |
|---|---|
| `Input/IInputSource` | 输入源接缝（多人网络接缝：NetworkInputRelay 实现后仿真零改动） |
| `Input/PlayerInputSource` | 设备→指令；点按/长按内部状态；停用前保存设备配对、激活时恢复（附身往返的设备归属） |
| `Input/AI/AITreeInputSource` | 决策树→意图→指令；低频决策防抖；MeleeAttackRange/Interval 近战规则；被附身身体防写入（双保险） |
| `Input/AI/Decision/` 四件（Decision/Selector/Leaf/Branch） | 决策机械：优先级选择，返回 null 维持现状（防抖）——纯 C# 无 Unity 依赖 |

**放置规则**：新输入来源（回放/网络中继）= 实现 IInputSource，经 `Brain.BindInputSource(实例)` 绑定
（null 回落 AI 源）；新 AI 行为 = DecisionLeaf 加进 BuildDecisionTree（决策树数据化后置）。

## 5. 数据模板域（`Templates/`，ScriptableObject，共享模板绝不运行时改）

| SO | 声明什么 |
|---|---|
| `Templates/CharacterConfigSO` | 体质（MaxHealth/FaithCapacity/FaithLossPerHit/FactionId）+ 手部容量 |
| `Templates/WeaponSO` | 武器类型/容量占用/攻速/挥剑受伤乘数/出招表引用/护甲套装联动 |

| `Templates/ArmorSO` / `ArmorSetSO` | 护甲部位与所属套装 / 档位表（件数门槛→ModifierEffect） |
| `Templates/SkillSO` | 技能：阈值/冷却/普通与强化攻击段/三组效果列表/驱散配置 |
| `Templates/ModifierEffect` | 效果三成分（控制/数值/周期）+ 标签 + 信心周期 + 冠冕吸血 |

**放置规则**：新武器/新 buff/新技能/新角色 = 一份 SO 资产，零代码（特殊语义才考虑子类，先例
PossessionEffect）。模板/实例分层：运行时状态一律在 §3 的黑板里，SO 只读。

## 6. 推导/投影域（Logic 纯 C#：从一块状态推导另一块）

| 类 | 从什么推导什么 | 触发时机 |
|---|---|---|

| `Logic/FaithEvent`（CrownEvent/TideEvent） | 玩法事件 → 信心写入 | 命中/受击/周期/配置事件 |

## 11. 已知越权与漂移点（与 2026-10-03 审视衔接）

1. ✅ **已解决（2026-10-03）层槽写权收口**：ModifierList 不再直写状态机——`ActiveControlKind` 报数、
   `Brain.SyncControlProjection` 统一写入（事件驱动回调，"失控当帧压制"时序契约不变，相关测试零改动）。
   层槽写者现为两个：状态自身转换 + Brain。
2. Brain 按 `is not EntityAttackState` 旁路转向（建议 LocksTurning 能力声明）。
3. ✅ **已解决（2026-10-03）Brain 隐式黑板拆出**：ActivePossession/DeathView/LastSkillCast 归 Entity
   （PossessionLink 提为顶级 internal 类），Brain 留只读转发。
4. `CanAct` 是 `CanUseSkill` 的冗余别名。
5. FaithEvent 每次结算分配一次性对象（玩法路径零分配纪律的缺口）。
